Family Beacon — Try mode (ntfy transport)

Status: v0.1 (Draft)

A second transport for Family Beacon that needs no server: the family's devices
exchange the same end-to-end-encrypted `beacon-protocol` envelopes over an ntfy
instance — public (ntfy.sh) or self-hosted — instead of over Sund's blind queues.
Install, scan a QR, done. Nothing to provision, no domain, no DNS, no box that
has to stay up.

Try mode exists to remove the setup cliff between "this looks interesting" and
"my family is using it", **not** to be a second supported way to run Family
Beacon forever. It is deliberately weaker than Sund on two guarantees that
matter, it does not help iOS at all, and graduating to Sund re-pairs every
device. All three facts are surfaced to the user rather than smoothed over — see
Honesty rule.

This document specifies the mode. Sund remains the backend; ARCHITECTURE.md's
profiles A and B remain the deployment story. Try mode is a third thing, below
both.

---

The problem it solves

Family Beacon's adoption threshold today is a server. Even profile A — one
`docker compose up -d` — presupposes someone in the family who owns a machine
that stays on, is comfortable with Docker, and is willing to be the operator
before anyone has seen the product work. Profile B additionally presupposes a
domain and DNS. That is a large ask in exchange for an unknown, and it is asked
at exactly the wrong moment: before the family has any evidence the app is worth
the trouble.

Try mode inverts the order. The family uses the product first, on infrastructure
nobody has to own, and the server question arrives later — when the answer is
"yes, and now I want the stronger guarantees" rather than "maybe, if I set up a
server first."

---

Where the seam goes

The layering in `FamilyBeacon-Protocol.md` already separates `beacon-protocol`
(envelope, message types, consent state machine, transparency ledger — nothing
transport-specific) from `sund-client` (identity, pairing, sessions, queues,
push). Try mode is a **sibling of `sund-client`**, not a fork of anything above
it:

    Family Beacon apps        UI, notifications, policy, SOS escalation
    ─────────────────────────────────────────────────────────────────
    beacon-protocol           envelope codec, types, consent, ledger
    ─────────────────────────────────────────────────────────────────
    family roster             membership, introductions, revocation policy
    ─────────────────────────────────────────────────────────────────
    transport port            send / subscribe / ack  (the interface)
    ─────────────────────────────────────────────────────────────────
    sund-client  │  ntfy-client        two implementations
    ─────────────────────────────────────────────────────────────────
    Sund server  │  ntfy instance

The transport port

Narrow on purpose. It carries what `beacon-protocol`'s Transport assumptions
section already asks for and nothing more:

    send(channel, ciphertext, priority, ttl) → message_id
    subscribe(channel) → stream of (message_id, ciphertext, received_at)
    ack(channel, message_id)
    channel lifecycle: open(channel), retire(channel)

Both backends satisfy it. Delivery stays at-least-once and per-channel ordered;
cross-channel order stays undefined. The protocol's existing dedupe ids and
sequence numbers already absorb the difference.

The rule that keeps this honest

**Management-plane capability stays above the port, never inside it.** Sund has
a management plane — device registry, key bundles, invitations, server-enforced
revocation — and ntfy has no analogue for any of it. The temptation is to widen
the port until both fit. Don't: that designs Sund mode down to ntfy's level and
buys nothing.

Instead, membership, introductions and revocation become explicit client-side
logic (the *family roster* layer above the port), and **Sund mode uses its
management plane as a stronger implementation of that same logic** — server-side
key kill and queue retirement in addition to the client-side rotation, not
instead of it. Try mode gets the client-side half only. The difference is real
and is stated to the user; it is not abstracted away.

This is also what finally makes `sund-client` genuinely reusable, which open
decision #6 wants anyway: a second consumer of the port proves the boundary is
where the layering doc claims it is.

---

Try mode concretely

Topics

ntfy topics are bearer capabilities: knowing the name grants publish and
subscribe (on ntfy.sh there is no other access control). Try mode therefore
treats every topic name as a secret and derives all of them, so none is ever
transmitted after the initial join:

    family_secret        256-bit, generated by the founding device
    epoch                integer, starts at 0, bumped on membership change

    T_family             = HKDF(family_secret, "family",  epoch)
    T_inbox(device_id)   = HKDF(family_secret, "inbox",   device_id, epoch)

Each device subscribes to its own inbox and to the family topic. A pair channel
in the protocol's sense is "publish to the peer's inbox" — duplex, per-pair,
exactly as the transport assumptions require. Nothing is ever published to a
topic derived from a secret the publisher does not hold, so topic knowledge
tracks family membership by construction.

The family topic is the one exception to "group semantics do not exist on the
wire" (Protocol → Transport assumptions), and it is narrow: it carries
membership coordination only — join announcements, roster updates, epoch bumps —
encrypted to the family secret. **No content type ever travels on it.** Location,
battery, SOS, attention, geofence, consent and config all go per-pair to inboxes,
under per-pair session keys, unchanged.

Note that Try mode talks to ntfy *directly* rather than through the generic
UnifiedPush abstraction, because it needs both publish and subscribe and needs to
choose its own topic names. On Android the inbox subscription doubles as the push
wake-up — in Try mode transport and push are the same channel, which is a genuine
simplification over Sund mode's separate push leg.

The join QR

    beacon+ntfy://<host>[:port]#<join-secret>

Plus, in the same QR payload: the inviting device's identity public key and the
mode version. The fragment carries a **secret**, unlike profile A's fragment
which carries a (non-confidential) certificate fingerprint. Consequence, and it
is normative: this address form is QR-only. It must never be presented as a
copyable link, sent over a messaging app, or written to a log — the clients treat
it as a credential, and it expires.

Note what the QR does *not* contain: the family secret. A leaked QR lets someone
*ask* to join; it does not give them the family's traffic topics, and it does not
survive the approval step below.

The join ceremony

1. An existing member M generates a one-time join secret `s`, derives
   `T_join = HKDF(s, "join")`, and displays the QR.
2. The joining device J subscribes to `T_join` and publishes a signed join
   request: J's identity public key plus an ephemeral key.
3. Both screens display a short authentication string derived from both identity
   keys and `s`. **A human compares them and approves on M's device.** ntfy
   cannot enforce single-use or short-TTL invitation tokens the way Sund does, so
   the enforcement is a person — which is the ceremony the product wants anyway
   (design guide: physical co-presence is the trust ceremony).
4. M sends J, over the channel just authenticated: the family secret, the current
   epoch, and the roster (each member's identity key, display name, device id).
5. J derives its inbox, subscribes, and announces itself on `T_family`. Each
   existing member establishes a pairwise session with J.
6. `T_join` is abandoned and `s` is burned on both devices.

One QR per joining device — the same ceremony count as Sund mode, not the
O(N²) pairwise scan the shape first suggests.

Priority and TTL

ntfy's `Priority` header carries the protocol's classes: `sos`/`sos_clear` at
max, `attention` at high, everything else default. TTL is **not** expressible —
ntfy has a server-configured cache window and no per-message expiry — so time-to-
live is enforced at the receiver from the envelope's `sent` field, and the mode
documents that the server-side retention floor is the instance's cache setting,
not the sender's intent. `Cache: no` is not the answer: it would deliver only to
devices that happen to be online, breaking store-and-forward entirely.

Message size

ntfy.sh's default message size limit is ~4 KB against the protocol's 64 KiB
assumption. Try mode caps ciphertext at 3 KB and refuses (and ledgers) anything
larger. Every v1 message type fits comfortably; the cap is a real constraint only
for future types, which is another reason media stays out of v1 regardless.

Rotation and revocation

Removing a device means bumping the epoch: every inbox and the family topic move
to names the removed device cannot derive. This is the client-side half of
revocation, and it has a cost Sund mode does not pay — **a member who is offline
when the epoch bumps is still listening on the old topics and does not know.** A
grace period covers the ordinary case (a device left the family amicably), but a
bump prompted by a lost or hostile device cannot keep the old topics alive
without defeating itself. Those members must be re-admitted by the join ceremony.
The UI says so before the user confirms the removal.

---

What survives unchanged

The whole of `beacon-protocol`: envelope, every v1 message type, the consent
state machine, the ledger rule, the test vectors. The session primitive
(open decision #1 in the protocol doc) is shared — Try mode changes what carries
the ciphertext, never what is inside it. The E2EE stance holds without bending:
ntfy is *also* a blind relay here, seeing exactly what Sund sees minus
unlinkability.

---

What degrades — honestly

Two of these are serious enough on their own to keep Try mode a trial:

1. **Messages are lost past the cache window.** Sund holds a message until its
   TTL expires or the recipient acks it. ntfy caches for a server-configured
   window (~12 h on ntfy.sh) and then drops it. A phone that is off for a weekend
   permanently misses everything sent to it. This is tolerable for `location`
   (a stale fix is worthless anyway) and not tolerable for `consent_update`,
   `sos_clear` or `config_update`, where missing a message leaves two devices
   disagreeing about state. Mitigation is client-side reconciliation on
   reconnect, not a fix.

2. **Revocation is not server-enforced.** Sund kills a revoked device's identity
   key and queue access immediately; it is the only server-side remedy against a
   member turned hostile (Sund-PRD → Threat model). Try mode has epoch rotation
   only, it needs every remaining member to participate, and the removed device
   keeps whatever it already decrypted.

And then:

- **A topic name is a bearer capability.** Leaking one gives an outsider the
  ciphertext stream, full timing and size metadata, and the ability to inject
  noise into an inbox. Forged content is still impossible — the session layer
  authenticates senders — but the noise is a real denial-of-service surface with
  no per-sender throttle.
- **The operator sees the family graph.** Sund deliberately stores no
  sender-to-recipient link. In Try mode every message to a member lands on that
  member's topic, so the instance operator can read the family's communication
  graph directly from topic activity. This is a metadata regression, not a
  confidentiality one, and it is the sharpest privacy difference between the
  modes.
- **Retention is the operator's choice, not the family's.**
- **No quota, no abuse controls, no availability commitment** — on ntfy.sh, a
  free public service the family has no relationship with.

---

What it does not solve: iOS

Try mode removes the server for Android and web. It does nothing for iOS.

ntfy's own iOS app carries an APNS key bound to *its* bundle identifier; a
different app cannot use it, and iOS permits no third-party push distributor at
all (Sund-PRD → Push architecture). So an iOS Family Beacon client in Try mode
still needs a vendor-operated APNS gateway for wake-ups, exactly as CLAUDE.md
decision #2 describes — or it runs in a degraded foreground-and-opportunistic-
refresh mode with unbounded delivery latency.

Realistically, Try mode is "an Android (and web) family is running in five
minutes." That is worth saying in the onboarding copy rather than letting an
iPhone household discover it after pairing.

---

Honesty rule (normative)

**The abstraction must not hide the downgrade.** A swappable transport that
renders identically in the UI would hand the user weaker revocation and retention
guarantees without telling them — which is the same failure mode ETHICS.md
forbids elsewhere: presenting a state that is not the true one.

Therefore:

- The mode is named and explained in onboarding, before the first pairing, with
  the two serious degradations stated in plain language.
- The limits are restated at the moments they bite: removing a device (offline
  members may need re-admission), and the SOS arming screen (Try mode adds a
  delivery dependency on a third-party service the family does not control, on
  top of the best-effort limit that already holds in every mode).
- **The transparency ledger records the transport mode**, so a user can always
  tell which guarantees a given message travelled under.
- The app never presents Try mode as equivalent to a Sund deployment, and never
  auto-selects it for a family that already has a server.

The existing SOS rule is unchanged and unweakened: no guaranteed delivery, and
never a route to emergency services (ETHICS.md → Safety limitations). Try mode
does not get a softer version of that sentence — it gets an additional one.

---

Graduating to Sund

Moving from Try mode to a Sund deployment is a **re-pairing event**: every device
re-onboards against the new server address, exactly as switching between
deployment profiles A and B is (Sund-Pinning-Contract §8.5). Nothing about the
family's identity or history transfers automatically — local ledgers, consent
state and geofences stay on their devices; the family is reconstituted by the
ordinary join ceremony against Sund.

This is the cost that makes Try mode a trial rather than a tier, and it is stated
up front, at first run — a family that trials for a month and then has to
re-onboard four devices should have known that on day one.

---

Open items

1. **Reconciliation after cache-window loss.** `consent_update` and `config_update`
   need a state-resync-on-reconnect mechanism for Try mode to be merely weaker
   rather than incorrect. Likely a periodic signed digest of grant state per pair,
   which Sund mode would also benefit from. Blocking for Try mode.
2. **Epoch bump coordination** when members are offline: grace-period length, how
   a stranded member is detected and re-admitted, and what the UI shows meanwhile.
3. **Self-hosted ntfy with auth/ACL** as a middle rung between ntfy.sh and Sund —
   it removes the bearer-capability and third-party-operator problems while
   keeping the cache-window and revocation ones. Worth specifying, or worth
   refusing as a rung too many?
4. ~~Whether Try mode ships at v1 or after.~~ **Decided July 2026: after.** Not
   before Sund mode works end to end. Try mode is additive and touches no
   normative guarantee, so deferring costs nothing, while building it against an
   unproven transport layer costs a lot — until the first implementation ships
   there is nothing for the port to be honest about. The port is still defined
   now: it doubles as the seam that lets the client libraries be unit-tested
   against an in-memory transport, so it pays for itself before ntfy-client
   exists. The test-vector discipline must then cover both transports.
5. **Scope limiting.** Should Try mode refuse to enable some feature set — for
   instance geofence notifications, whose value depends on reliable delivery —
   rather than offering everything at lower reliability?
